マウスのボタンを押したら、別の動作に差し替える。押されたことを受け取って、代わりのイベントを送る。**それだけのアプリを作るつもりだった。**

終わってみると、macOS の API を6つ束ねていた。しかも**7つ目があることに、あとから気づいた**。

理由ははっきりしている。**macOS は「マウスのボタン」という概念を、1箇所で持っていない。**

前編（[macOS は「どのマウスのボタンか」を教えてくれない](https://zenn.dev/brainy_software/articles/macos-cannot-tell-which-mouse)）では、入力を**受け取る**側を書いた。この記事は**返す**側と、そこから先で足りなかったものの話になる。

## 前編のおさらい ── 入力が通る道

マウスのボタンが押されてからアプリに届くまで、入力は層をいくつか通る。

```
  マウス（HID デバイス）
        │  USB / Bluetooth
        ▼
  IOKit / IOHIDFamily  ──────  IOHIDManager で覗ける
        │
        ▼
  Quartz Event Services ─────  CGEventTap で覗ける・止められる
        │              ▲
        ▼              │  作ったイベントを post して返す
   アプリケーション ───┘
```

| 層 | どのマウスか分かる | 止められる | イベントを作って流せる |
|---|---|---|---|
| **IOKit**（`IOHIDManager`） | **分かる** | 占有すれば（採らなかった） | ─ |
| **Quartz**（`CGEventTap`） | **分からない** | **できる** | **できる** |

**「誰が押したか分かる層」と「止められる層」が別々にあり、繋ぐ公式な API が無い。**前編では、両方を並行して監視し、**50ms 以内に届いた同じボタン番号**を突き合わせることで「どのマウスのどのボタンか」を判定した。

ここまでで2つ ── `CGEventTap` と `IOHIDManager`。

## 1. 返す ── 作ったイベントは、本物と同じでないと効かない

「押された」を受け取れた。次は**代わりのイベントを作って OS に返す**。

`CGEvent` を作って `post` するだけ ── のはずだった。

```swift
guard let down = CGEvent(keyboardEventSource: source, virtualKey: resolved.keyCode, keyDown: true),
      let up   = CGEvent(keyboardEventSource: source, virtualKey: resolved.keyCode, keyDown: false)
else { return }

down.flags = flags
down.post(tap: .cghidEventTap)
```

`Command+Shift+4`（スクリーンショット）は、これで動いた。

**`Control+Option+↑` は、まったく反応しなかった。**

同じコードで、送り先も同じ。文字キーは効いて、矢印キーだけ効かない。7通りの組み合わせを試した ── イベントの発生源を変える、post 先を変える、修飾キーを別イベントで送る。**全部外した。**

原因はどれでもなく、**フラグだった。**

`.listenOnly` のタップを張って、**本物のキーボードで `Control+Option+↑` を押したときのイベントを観測した。**値はこうだった。

```
flags = 0xac0121
```

内訳を1ビットずつ突き合わせる。

| ビット | 意味 |
|---|---|
| `0x00040000` | Control |
| `0x00080000` | Option |
| `0x00200000` | **NumericPad** ← 立っている |
| `0x00800000` | **SecondaryFn** ← 立っている |
| `0x00000100` | NonCoalesced |
| `0x00000001` / `0x00000020` | 左 Control / 左 Option |

**macOS では、矢印キーが「テンキー扱い＋Fn 扱い」になる。**修飾キーのマスクを2つ立てただけでは、本物と同じ形になっていない。ホットキーを登録しているアプリは、その差を見て弾いていた。

```swift
var flags: CGEventFlags = [.maskNonCoalesced]
for modifier in resolved.modifiers {
    flags.insert(flag(for: modifier))
    flags.insert(deviceFlag(for: modifier))   // 左右の区別
}
if KeyMapper.isNumericPad(resolved.keyCode) {  // 矢印キー
    flags.insert(.maskNumericPad)
    flags.insert(.maskSecondaryFn)
}
```

**OS は「それっぽいイベント」を受け付けない。**受け取る側が見ているフィールドが1つでも違えば、無視される。

教訓のほうが本体だと思っている ── **合成したイベントが効かないとき、推測で組み合わせを変えない。**`.listenOnly` のタップで**本物を観測して、フィールドを1つずつ突き合わせる**。7通り試した時間より、観測した5分のほうが短かった。

これで3つ目 ── `CGEvent` の post。

## 2. 道の外で、さらに要ったもの

ここまでが入力の経路である。だが**経路の外側にも API が要った。**

**レポート記述子を読む。**HID デバイスは接続時に「私はこういう入力を出します」と OS に申告する。これが**レポート記述子**で、`ioreg` で読める。マウスのボタンが何番まであるのか、ホイールの傾きがボタンなのかスクロールなのかは、**ここに書いてある**。実際に読むと、手元のトラックボールは `Usage Page(Button) / Usage Min(1) / Usage Max(16)` ── **ボタン16個ぶんの枠**を宣言していた。ホイールの傾けはボタンではなく `Consumer / AC Pan`（水平パン）として届くことも、ここで分かった。**ボタンとして探している限り、永久に見つからない。**

**前面のアプリを知る。**アプリごとに割当を変えるなら、いま何が前面にいるかが要る。これは入力とは無関係の層で、`NSWorkspace` を使う。

```swift
let bundleId = NSWorkspace.shared.frontmostApplication?.bundleIdentifier
```

**権限を2つ取る。**`CGEventTap` を張るには**入力監視**、他のアプリにイベントを送るには**アクセシビリティ**が要る。macOS の許可の仕組みを **TCC**（Transparency, Consent, and Control）と呼ぶ。

ここには実装上の罠がある。`AXIsProcessTrusted()` と `CGPreflightPostEventAccess()` は**プロセスごとにキャッシュされる**。初回呼び出しでキャッシュが埋まり、**起動後に許可を与えても false を返し続ける**。変更を知らせる通知 API も無い。結果として「許可する → 何も起きない → まだ足りませんと言われる」の袋小路ができる。

いま採っている回避策は、**実際にタップを張ってみて、成否で判定する**というものである（RunLoop に載せずその場で捨てるので、入力には触れない）。**タップの作成は毎回 TCC を引くので、キャッシュの影響を受けない。**

ここまでで6つになった。

## 3. 7つ目の経路

`CGEventTap`、`CGEvent` の post、`IOHIDManager`、レポート記述子、`NSWorkspace`、権限の API。

**これで全部だと思っていた。**

手元のトラックボールには、ボール手前に小さなボタンがある（押すとカーソル速度が落ちる「プレシジョンボタン」）。ここにも何か割り当てようとした。**押しても、何も起きなかった。**

`CGEventTap` のログに出ない。`IOHIDManager` のログにも出ない。フィルタの手前 ── コールバックに入った直後で生の値を出しても、**そもそも1回も呼ばれない**。

記述子には**ボタン16個ぶんの枠がある**のに、実際に届くのは5個だけだった。そこでこう結論した ── **枠はあるのに乗ってこない。マウスが OS に出していない。**

**間違いだった。**

このボタンを設定できる macOS 用のユーティリティは実在していて、**実機で普通に動いている。**押下を受け取れている以上、どこかには届いている。

記述子をもう一度見ると、3行目にこう書いてあった。

```
06 43ff  85 11  95 13   Vendor Page 0xFF43 / Report ID 0x11 / 19 バイト
```

`0xFF00` 以降は**ベンダー定義ページ**で、意味はメーカーが自由に決めてよい領域である。`0xFF43` はロジクールの **HID++** として知られている ── 汎用の HID とは別建ての、機種ごとのコマンド体系を持ったプロトコルで、DPI・バッテリー・ボタンの再割当といった「標準の HID では表現できないもの」がここを通る。

つまり、**標準の入口が閉じているのではない。別の入口が開いていて、こちらは片方しか見ていなかった。**

「届いていない」と「自分が見ていない」は、**観測結果としては同じ形をしている。**区別するには、外の世界に同じことをやれている実装があるかを見るしかなかった。

> ここは推測を含む。断定できるのは「**標準の Button ページには来ない**」までで、「HID++ 側に流れている」はレポート記述子のベンダーページと、他社製品が実機で扱えている事実からの推論である（こちらが HID++ を叩いて確認したわけではない）。

追うかどうかは別の判断になる。HID++ に入ると**機種ごとのコマンド表**を持つ道に入る ── ボタン1個のために機種の数だけ対応表を書き、機種が増えるたびに追記する仕事を引き受けることになる。しかもロジクールの体系なので、他社ではまた一式増える。**いまは追っていない。取りに行けないのではなく、取りに行っていない。**

## 4. なぜ、こうなっているのか

macOS は「マウスのボタン」という概念を1箇所で持っていない。デバイスの層（IOKit）とイベントの層（Quartz）が別々にあり、両者を結ぶ API が無い。

**これは欠陥ではないと思っている。**

Quartz の仕事は、**デバイスを抽象化して消すこと**である。テキストエディタが「どのメーカーのマウスでクリックされたか」を気にせずに済むようにするのが、この層の存在意義になる。**デバイスの情報を落とすのが正しい設計**であって、落とされた情報を必要とするアプリのほうが例外なのだ。

例外の側に立つと、こうなる。

| # | 何のために | 使うもの |
|---|---|---|
| 1 | イベントを止める・通す | `CGEventTap` |
| 2 | イベントを作って返す | `CGEvent` + `post` |
| 3 | どのマウスか識別する | `IOHIDManager` |
| 4 | ボタン番号の意味を知る | HID レポート記述子 |
| 5 | 前面のアプリを知る | `NSWorkspace` |
| 6 | 権限を確認する | TCC 関連の API |
| （7） | 標準に来ない入力を拾う | ベンダー独自プロトコル（**見送り**） |

**1つのボタンを差し替えるために6つ。**そして7つ目は、あるのに使っていない。

まとめるとこうなる。

- **「誰が押したか分かる層」と「止められる層」は別。**繋ぐ API は無いので、自分で縫う
- **どちらが先に届くかを最初に測る。**順序が逆なら設計ごと成立しない
- **合成したイベントは、本物と同じフラグでないと効かない。**推測せず `.listenOnly` で本物を観測する
- **タップは黙って切られる。**再登録は必須
- **権限の確認結果はキャッシュされる。**「許可したのに気づかない」はこれが原因
- **「届いていない」と「自分が見ていない」は同じ形で観測される**

### 用語

| 語 | 意味 |
|---|---|
| **HID** | Human Interface Device。入力機器が共通で使う規格 |
| **IOKit / IOHIDFamily** | macOS がデバイスを扱う土台。どの機器かを知っている層 |
| **Quartz Event Services** | OS がアプリにイベントを配る仕組み。デバイス情報は入っていない |
| **`IOHIDManager`** | IOKit の層を覗く API。機器の一覧と入力が取れる |
| **`CGEventTap`** | Quartz の層に割り込む API。書き換え・握りつぶしができる |
| **`CGEvent` の post** | 作ったイベントを OS のイベント列へ流し込むこと |
| **usage / Usage Page** | HID で「この値が何を意味するか」を表す番号と、その分類 |
| **レポート記述子** | デバイスが接続時に申告する「私はこういう入力を出します」の宣言 |
| **TCC** | macOS の許可の仕組み（入力監視・アクセシビリティ等） |
| **HID++** | ロジクール独自のプロトコル。標準 HID で表現できない機能が通る |

---

ここまでの6つを全部束ねると、「メーカーが違うマウスを、1つのアプリで設定する」ができる。作ったものは **[MouseForge](https://mouseforge.jp)** という常駐アプリで、macOS 26 で動いている。
