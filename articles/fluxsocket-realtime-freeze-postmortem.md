社内で使っているタスク管理ツールが、通知を5件同時に受け取っただけでフリーズしました。15件同時削除ではタブごとクラッシュ。原因の調査と対処に丸一日かかったので、同じ地雷を踏まないための記録を残しておきます。

WebSocketでリアルタイム通知を実装しているプロジェクトなら、規模を問わず起こりうる問題です。

## 構成と前提

このツールは、WebSocketでタスクの変更をリアルタイム同期します。複数人がブラウザで開いていると、誰かの変更が即座に全員の画面に反映されます。構成はシンプルです。

- **WebSocket接続**: pusher-jsクライアントでPublic Channelを購読
- **受信イベント**: タスクの `created` / `updated` / `deleted`
- **受信時の処理**: トースト通知の表示 + 該当行のハイライトアニメーション + タスク一覧の再描画

1-2件の通知なら何の問題もありません。ブラウザを開きっぱなしにしておけば、誰かがタスクを更新したタイミングでスッと画面に反映される。リアルタイム同期の理想的な体験です。

問題は「同時に大量の通知が来たとき」に起きました。

## 問題の発生

ある日、タスクの整理をしていて15件のタスクを一括削除しました。すると、別タブで開いていたその画面が完全にフリーズ。数秒待ってもブラウザが応答せず、最終的にタブがクラッシュしました。

再現条件を整理するとこうなりました。

| 同時通知数 | 挙動 |
|:---:|------|
| 1-2件 | 正常 |
| 3件 | やや引っかかる |
| 5件以上 | フリーズ |
| 15件 | タブクラッシュ |

「リアルタイム通知なのに、通知が来るとアプリが壊れる」という本末転倒な状態です。

## 初期調査: トーストの無限ループ

まず目を付けたのはトースト通知のコードでした。画面上に表示するトーストの数を制限する処理がこうなっていました。

```javascript
// 上限を超えたトーストを除去する処理
while (container.children.length > MAX_TOASTS) {
    dismiss(container.children[0]);
}
```

一見すると問題なさそうに見えるかもしれません。でも `dismiss()` の中身を見ると問題が分かります。

```javascript
function dismiss(el) {
    el.classList.add('removing');       // フェードアウトアニメーション開始
    el.addEventListener('animationend', function () {
        el.parentNode.removeChild(el);  // アニメーション完了後にDOM除去
    });
}
```

`dismiss()` はCSSアニメーションの完了を待ってからDOM要素を除去する**非同期処理**です。一方、`while` ループは**同期的**に `children.length` を評価し続けます。

つまり、`dismiss()` を呼んでもアニメーションが終わるまでDOM要素は残ったまま。`children.length` は減らない。`while` ループは永遠に回り続ける — **無限ループ**です。

### 修正

上限を超えた分はアニメーション不要と割り切り、即座にDOMから除去するように変更しました。

```javascript
while (container.children.length > MAX_TOASTS) {
    var oldest = container.children[0];
    clearTimeout(oldest._dismissTimer);  // 自動消去タイマーもクリア
    container.removeChild(oldest);        // アニメーションなしで即除去
}
```

これでトーストの無限ループは解消しました。

## 修正しても15件でフリーズする

トーストの修正後、改めてテストしてみました。

- 3件同時 → OK
- 5件同時 → OK
- 15件同時削除 → **フリーズ再発**

トーストは部分的な原因でしかなかったのです。

## 根本原因: DOM更新の集中砲火

15件の通知が同時に届いたとき、ブラウザの中で何が起きていたかを整理します。

1. **`toast.show()` x 15** — トースト要素のDOM生成が15回
2. **`highlight.fadeOut()` x 15** — 該当行のCSSアニメーションが15個同時起動
3. **`render()` x 15** — タスク一覧の全体再描画が15回トリガー

ここで致命的なのは、3番目の `render()` がタスク一覧のDOM全体を作り直す処理だったことです。15件のイベントそれぞれが `render()` を呼び出すので、DOMの破棄と再構築が15回繰り返されます。

さらに、2番目のハイライトアニメーションが参照しているDOM要素が、3番目の `render()` によって消えてしまう。存在しない要素へのスタイル操作が走り、ブラウザはレイアウトの再計算を繰り返す — いわゆる**レイアウトスラッシング**が発生していました。

:::message
**レイアウトスラッシングとは**
ブラウザがDOM変更→レイアウト再計算→DOM変更→レイアウト再計算...を短時間に繰り返す現象です。通常はブラウザがDOM変更をまとめて処理してくれますが、特定の操作（要素のサイズ取得など）を挟むと強制的に再計算が走り、パフォーマンスが激しく劣化します。
:::

## 調査した6つの対処パターン

闇雲に修正する前に、リアルタイムUIの大量更新に対するアプローチを調べてみました。

| # | パターン | 概要 | 代表的な採用例 |
|:---:|---------|------|------|
| 1 | rAFバッチング | バッファに溜めて `requestAnimationFrame` でまとめてDOM更新 | Socket.io公式推奨、React 18 Batching |
| 2 | Web Worker | WebSocket受信処理を別スレッドに分離 | Slackデスクトップアプリ |
| 3 | 通知キュー+サマリー集約 | 超過分を「他N件」にまとめて表示 | Discord、GitHub Notifications |
| 4 | requestIdleCallback | ブラウザのアイドル時間にまとめて更新 | React 18 startTransition |
| 5 | サーバーサイド集約 | 短時間のイベントをサーバー側でバンドル送信 | Ably Message Bundling |
| 6 | 仮想スクロール | 画面に見えるDOMだけを保持 | Twitter/Xタイムライン |

それぞれ適した場面が異なります。簡単に整理してみます。

**パターン1（rAFバッチング）** は、フレーム単位でDOM更新を集約する手法です。実装が軽く、既存コードへの影響も小さいので、まず試してみるのに向いています。

**パターン2（Web Worker）** は、WebSocketの受信処理自体をメインスレッドから切り離します。受信量が非常に多い場合（毎秒数十件以上）に有効ですが、Worker間のデータ受け渡しにオーバーヘッドがあります。

**パターン3（サマリー集約）** は、通知のUXとして自然です。DiscordやGitHubが「他N件の通知」とまとめて表示しているのをイメージしてもらえれば分かりやすいかもしれません。

**パターン4（requestIdleCallback）** は、更新の優先度が低い場合に適しています。ただし、リアルタイム通知は「すぐ反映してほしい」ものなので、今回のケースではやや遅延が気になります。

**パターン5（サーバーサイド集約）** は効果が高い一方、サーバー側の改修が必要になります。クライアント側だけで対処したい場合には選びにくい選択肢です。

**パターン6（仮想スクロール）** は、表示件数が数百件を超えるような場面で威力を発揮します。今回のように数十件程度であれば、まだ必要ないかもしれません。

## 採用した対処: パターン1 + 3

今回はパターン1（rAFバッチング）とパターン3（トーストサマリー集約）を組み合わせました。実装の軽さと効果のバランスがよく、既存コードの大幅な書き換えが不要だったのが決め手です。

### rAFバッチング: イベントをキューに溜めてまとめて処理

イベントを受信したら即座にDOM操作するのではなく、キューに溜めます。`requestAnimationFrame` のタイミング（約16ms間隔）でまとめて処理することで、15件同時でも1フレームで1回のDOM更新に集約されます。

```javascript
var messageQueue = [];
var rafScheduled = false;

function enqueueMessage(type, data) {
    messageQueue.push({ type: type, data: data });
    if (!rafScheduled) {
        rafScheduled = true;
        requestAnimationFrame(processQueue);
    }
}

function processQueue() {
    // キューを一括取得してクリア
    var batch = messageQueue.splice(0);
    rafScheduled = false;

    // バッチ内の全イベントを反映してから1回だけ再描画
    batch.forEach(function (msg) {
        applyUpdate(msg.type, msg.data);
    });
    scheduleRender();  // まとめて1回だけ
}
```

ポイントは `requestAnimationFrame` の特性です。ブラウザが次のフレームを描画する直前に1回だけコールバックが呼ばれるので、短時間に何件イベントが来ても処理は1フレームにまとまります。

### トーストサマリー: 大量通知を「他N件」にまとめる

トースト通知も同様に、短時間（300ms）のバッチウィンドウを設けて集約します。

```javascript
var toastBatchQueue = [];
var toastBatchTimer = null;

function scheduleToast(toastData) {
    toastBatchQueue.push(toastData);
    if (toastBatchTimer) return;  // 既にタイマー稼働中なら追加だけ

    toastBatchTimer = setTimeout(function () {
        var batch = toastBatchQueue.splice(0);
        toastBatchTimer = null;

        if (batch.length <= 3) {
            // 3件以下ならそのまま個別表示
            batch.forEach(function (t) { FluxToast.show(t); });
        } else {
            // 最新1件を表示 + 残りはサマリー
            FluxToast.show(batch[batch.length - 1]);
            FluxToast.show({
                message: '他 ' + (batch.length - 1) + ' 件の更新があります',
                type: 'info'
            });
        }
    }, 300);
}
```

3件以下なら個別に表示し、4件以上なら「最新1件 + 他N件の更新」にまとめます。Discordの通知に近い挙動です。

### 補助的な対策

上記に加えて、2つの調整を行いました。

- **renderのデバウンス間隔を80ms → 200msに延長**: 連続イベント時にrenderが走りすぎないようにする
- **ハイライトアニメーションの同時実行数を3件に制限**: 超過分はアニメーションなしで即座にスタイルを適用

## 結果

| シナリオ | Before | After |
|---------|--------|-------|
| 3件同時通知 | やや引っかかる | スムーズ |
| 5件同時通知 | フリーズ | スムーズ |
| 15件同時削除 | タブクラッシュ | フリーズなし、「他14件の更新」とまとめて通知 |

15件同時の登録・削除でもフリーズしなくなりました。

## この経験から学んだこと

今回の件で改めて感じたのは、**リアルタイム通知の実装は「受信」よりも「表示」が難しい**ということです。

WebSocketの接続やイベントの受信は、ライブラリがよくできているので比較的簡単にセットアップできます。でも「受信したデータをどうDOMに反映するか」の部分は、アプリケーション側の設計に委ねられています。

少量のイベントでは何も考えなくても動きます。問題が顕在化するのは、イベントが集中したときです。そして「イベントが集中するタイミング」は、一括操作や高負荷時など、ユーザーが最もストレスを感じやすい場面と重なります。

## セルフチェックリスト

最後に、リアルタイムUIを実装するときに確認してみるとよいポイントをまとめました。自分のプロジェクトに当てはめて、該当する項目がないか確認してみてください。

- [ ] イベント受信時に即座にDOM操作をしていないか（バッチ処理を検討）
- [ ] 全体再描画（render）がイベントごとに走っていないか（デバウンスを検討）
- [ ] CSSアニメーションの同時実行数に上限はあるか
- [ ] トースト通知が大量に表示されたとき、古い通知の除去は同期的に行われるか
- [ ] 非同期処理（アニメーション完了待ち等）を同期ループの中で呼んでいないか
- [ ] 10件以上のイベントが同時に来た場合のテストをしているか

上のチェックに1つでも引っかかったら、rAFバッチングやサマリー集約のようなパターンを導入してみるのが良いかもしれません。少量のイベントでは問題が見えないので、開発段階で意図的に負荷テストをしておくことをおすすめします。

:::message
この記事で紹介した問題は、WebSocket SaaS側の問題ではなく、クライアント側のDOM更新設計の問題です。Pusher、Socket.io、Ably、FluxSocketなど、どのWebSocket基盤を使っていても同様に起こりえます。
:::
