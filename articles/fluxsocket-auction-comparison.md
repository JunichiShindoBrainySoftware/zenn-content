## はじめに

「Web アプリをリアルタイムにしたい」と思ったとき、実現方法はいくつかあります。手動リロード、ポーリング、WebSocket — それぞれにメリットとデメリットがあり、**どれが最適かはユースケースによって異なります**。

この記事では、同じオークションアプリを3つの方式で実装したデモを使って、それぞれの仕組み・特性・適したユースケースを整理します。

「なんとなく WebSocket が良さそう」ではなく、**自分のプロジェクトにどの方式が合うか**を判断するための材料になれば幸いです。

## 3つの方式の仕組み

### 方式1: 手動リロード

```
クライアントA（入札）          サーバー              クライアントB
    |                           |                       |
    |-- POST（入札）----------->|                       |
    |<-- 200 OK（結果）---------|                       |
    |                           |                       |
    |   Aの画面は更新される      |   Bは何も知らない      |
    |                           |                       |
    |                           |   Bがリロード          |
    |                           |<-- GET /api/items ----|
    |                           |--- 200 OK ----------->|
    |                           |                       |
    |                           |   ようやくBに反映      |
```

最もシンプルな方式です。クライアントがデータを取りに行かない限り、画面は更新されません。

### 方式2: ポーリング

```
クライアントA（入札）          サーバー              クライアントB
    |                           |                       |
    |                           |<-- GET（ポーリング）---|  変化なし
    |                           |--- 200 OK ----------->|
    |                           |                       |
    |-- POST（入札）----------->|                       |
    |<-- 200 OK（結果）---------|                       |
    |                           |                       |
    |                           |<-- GET（ポーリング）---|  変化なし
    |                           |--- 200 OK ----------->|
    |                           |                       |
    |                           |<-- GET（ポーリング）---|  ここで反映
    |                           |--- 200 OK ----------->|
```

一定間隔でサーバーにデータを取りに行きます。データに変化がなくてもリクエストは毎回発生します。

### 方式3: WebSocket

```
クライアントA（入札）          サーバー          FluxSocket        クライアントB
    |                           |                 |                    |
    |                           |     WebSocket接続（常時維持）         |
    |                           |                 |<===== 接続 =======>|
    |                           |                 |                    |
    |-- POST（入札）----------->|                 |                    |
    |                           |-- イベント発火 ->|                    |
    |                           |                 |--- Push ---------> |
    |<-- Push ------------------|--- broadcast ---|    即座に反映       |
```

WebSocket 接続を常時維持し、サーバー側で変化があったときだけクライアントにプッシュします。クライアントがデータを「取りに行く」のではなく、サーバーから「届く」形です。

## 比較表

| 項目 | 手動リロード | ポーリング | WebSocket |
|:---|:---|:---|:---|
| **更新のタイミング** | ユーザーがリロードした時 | 設定間隔ごと（例: 3秒） | イベント発生時に即座 |
| **遅延** | ユーザー操作に依存 | 最大で間隔分（例: 最大3秒） | ほぼゼロ |
| **無駄なリクエスト** | なし | 多い（変化がなくても毎回） | なし（イベント駆動） |
| **サーバー負荷** | 低い | ユーザー数に比例して増加 | イベント発生時のみ |
| **実装の難易度** | 最も簡単 | 簡単（setInterval） | やや複雑（接続管理・認証） |
| **インフラ要件** | HTTP サーバーのみ | HTTP サーバーのみ | WebSocket サーバーまたは SaaS |
| **オフライン復帰** | リロードで復帰 | 自動で復帰 | 再接続ロジックが必要 |
| **閲覧者数の表示** | 困難 | 困難 | Presence Channel で容易 |

どの方式にも利点と制約があります。「WebSocket が常に正解」ではなく、プロジェクトの要件に合った方式を選ぶことが大切です。

## ユースケース別ガイド

### 手動リロードが適している場面

- **ブログや CMS の管理画面** — 記事の公開ステータスを確認する程度なら、リロードで十分
- **社内の申請・承認フロー** — 承認結果をリアルタイムで知る必要は通常ない
- **設定画面** — 変更を保存して結果を確認する用途

### ポーリングが適している場面

- **天気やニュースの表示** — 数分おきに更新すれば十分
- **バッチ処理の進捗確認** — 数秒間隔で完了チェックするだけ
- **同時利用者が少ない管理ツール** — サーバー負荷が問題にならない規模
- **WebSocket が使えないインフラ環境** — プロキシやファイアウォールの制約

### WebSocket が適している場面

- **チャット・メッセージング** — 送信したメッセージが即座に相手に届く必要がある
- **オークション・入札** — 他者の入札を即座に把握しないと不利になる
- **ダッシュボード・モニタリング** — サーバーメトリクスやアラートの即時反映
- **共同編集** — カーソル共有やドキュメントの同時編集
- **通知・アラート** — エラー発生やタスク完了の即時通知
- **投票・アンケートの集計** — 投票結果がリアルタイムでグラフに反映
- **IoT センサーデータ** — デバイスからのデータストリームを即時表示

## 応用例: リアルタイム化が効くユースケース

オークション以外にも、「手動リロード → ポーリング → WebSocket」の進化パターンが当てはまるユースケースは多くあります。いくつか具体的な例を挙げてみます。

### チャット・メッセージング

メッセージの送受信は、WebSocket の最も代表的なユースケースです。ポーリングでも実現はできますが、「入力中...」の表示や既読通知などは、WebSocket でないと自然な体験にならないでしょう。

| 方式 | 体験 |
|:---|:---|
| 手動リロード | メッセージを確認するたびにリロードが必要 |
| ポーリング | 数秒遅れでメッセージが届く。会話のテンポが悪い |
| WebSocket | 送信した瞬間に届く。「入力中...」も表示可能 |

### ダッシュボード・モニタリング

サーバーの CPU 使用率やアクセス数をリアルタイムで表示するダッシュボードは、更新頻度によって適切な方式が変わります。

| 方式 | 向いている場面 |
|:---|:---|
| ポーリング（長め） | 1分おきに概況を確認するレベル |
| ポーリング（短め） | 10秒間隔でトレンドを確認 |
| WebSocket | 秒単位のメトリクスをリアルタイムで可視化 |

更新頻度が1分に1回程度なら、ポーリングでも十分かもしれません。

### 共同編集（カーソル共有・ドキュメント同時編集）

Figma や Google Docs のような共同編集は、WebSocket なしでは成り立ちません。他のユーザーのカーソル位置やテキスト変更をミリ秒単位で共有する必要があるためです。

| 方式 | 現実性 |
|:---|:---|
| 手動リロード | 実用不可 |
| ポーリング | カーソルがカクカク動く。共同編集としては使えない |
| WebSocket | 滑らかなカーソル共有が可能 |

### 通知・アラート

エラー検知やタスク完了の通知は、数秒の遅延が許容されるケースも多いです。

| 方式 | 向いている場面 |
|:---|:---|
| ポーリング | メール通知の補助として。数十秒の遅延が許容される |
| WebSocket | 障害アラートなど即時性が求められる通知 |

### 投票・アンケートのリアルタイム集計

イベント会場でのライブ投票は、結果がリアルタイムでグラフに反映されると盛り上がります。一方、事後集計のアンケートならポーリングで十分です。

### IoT センサーデータ

温度・湿度・振動などのセンサーデータをリアルタイムでグラフに反映する場合は WebSocket が適しています。1時間おきの定点観測ならポーリングでも問題ありません。

## 判断のためのチェックリスト

自分のプロジェクトでどの方式が適切か、以下の質問で整理してみてください。

- [ ] 更新の遅延は何秒まで許容できるか？
  - 数十秒〜数分 → 手動リロードまたはポーリング
  - 数秒以内 → ポーリング（短間隔）
  - ほぼゼロ → WebSocket
- [ ] 同時接続ユーザーは何人程度か？
  - 10人以下 → ポーリングでもサーバー負荷は問題にならない
  - 100人以上 → ポーリングの負荷が気になり始める
  - 1,000人以上 → WebSocket の方が効率的
- [ ] データの更新頻度はどの程度か？
  - 低い（1日に数回） → 手動リロードで十分
  - 中程度（数分に1回） → ポーリング
  - 高い（秒単位） → WebSocket
- [ ] 「誰がオンラインか」の表示は必要か？
  - 必要 → WebSocket（Presence Channel）
  - 不要 → どの方式でも可
- [ ] WebSocket をサポートしないインフラ制約はあるか？
  - ある → ポーリング or Server-Sent Events
  - ない → WebSocket が選択肢に入る

## WebSocket を手軽に始めるには

WebSocket の実装で一番ハードルが高いのは、**WebSocket サーバーの構築と運用**です。接続管理、スケーリング、障害時の再接続処理など、HTTP サーバーとは異なる知識が求められます。

FluxSocket のような WebSocket SaaS を使うと、このインフラ部分を任せることができます。アプリケーション側は「チャネルを購読する」「イベントを発火する」というシンプルな API だけで、リアルタイム機能を実現できます。

FluxSocket は Pusher 互換なので、Pusher のクライアントライブラリ（`pusher-js`）やサーバー SDK がそのまま使えます。既存の Pusher の知識やコードがあれば、設定を変えるだけで移行できます。
