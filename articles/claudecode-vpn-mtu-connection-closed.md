## はじめに

ある日、VPN（NordVPN）に接続したまま Claude Code を使っていたら、長めの応答の途中で突然こんなエラーが出て止まるようになりました。

```
API Error: Connection closed mid-response
```

短いやり取りはまったく問題なく通るのに、応答が長くなると決まって途中で切れる。VPN を切れば再現しない。最初は「Anthropic 側の一時障害かな」と思ったのですが、調べていくうちに真因は **MTU（Maximum Transmission Unit）** にありました。

この記事は、その切り分けと対処を実体験ベースでまとめたものです。Claude Code に限らず、SSE（Server-Sent Events）やロングポーリングでストリーミングする AI ツールを VPN 越しに使っている方なら、同じ罠を踏む可能性があります。もし今まさに「AI ツールが VPN で固まる・切れる」状況なら、本記事の診断手順をなぞってみるのが良いかもしれません。

> ネットワーク用語に馴染みがない方向けの補足は、各セクションに「📘 ざっくり解説」として添えています。読み飛ばしても本筋は追えます。

## 症状：短い応答はOK、長い応答だけ途中で切れる

整理すると、症状はこうでした。

- **VPN 接続中だけ** 発生する（VPN を切ると再現しない）
- 短いプロンプト・短い応答は問題なく完走する
- 長い応答（コード生成や長文説明）の **途中** で `Connection closed mid-response` になる

ここで一番のヒントは「**サイズ依存**」だという点です。接続自体は確立できているし、認証も通っている。最初のデータは流れてくる。でも、ある程度大きなデータが連続して流れると止まる。

📘 **ざっくり解説：Claude Code の通信って何が流れてるの？**
Claude Code は Anthropic の API と通信していて、AI の応答は **SSE（Server-Sent Events）というストリーミング方式** で少しずつ届きます。チャットで文字がパラパラと出てくるのは、この仕組みのおかげです。そして長い応答になるほど、ネットワーク上では **MTU の上限いっぱいの大きなパケットが連続して** 流れることになります。だからこそ、経路の途中に「大きなパケットが通れない区間」があると、長い応答ほど影響を受けやすくなります。

「接続できないわけではないが、データが大きくなると止まる」——この挙動を見たら、まず疑うべきは **MTU とパケットのフラグメント（断片化）** です。

## 切り分けの勘所：サイズ依存なら MTU を疑う

ネットワークの不具合は「つながる／つながらない」の二択で考えがちですが、今回のように「**つながるが、大きいデータで止まる**」というパターンは、原因の方向性がかなり絞れます。

代表的な「サイズ依存の停滞」の犯人が **経路 MTU（Path MTU）の問題** です。

📘 **ざっくり解説：MTU とは**
MTU は「1つのパケットに載せられる最大サイズ」のことです。一般的なイーサネットでは 1500 バイト。手紙を送るときの「封筒1通に入れられる最大の枚数」のようなものだと考えると分かりやすいかもしれません。送りたいデータが大きいと、複数の封筒（パケット）に分けて送ります。

VPN を使うと、この封筒の中にさらに「VPN 用の包装（暗号化ヘッダなど）」が入ります。そのぶん中身に使える容量が減るので、**VPN トンネルの MTU は通常 1500 より小さくなります**。NordVPN の高速プロトコル NordLynx は WireGuard 系で、WireGuard の一般的なデフォルトは 1420 前後（1500−80）ですが、構成や経路によってさらに小さくなることもあります。今回の私の環境では、トンネルの MTU は実測で **1380 バイト** でした。

ここで問題になるのが、TCP が経路の MTU をどう把握するか、です。

## 再現可能な診断：DF付きpingで経路MTUを測る

推測だけでは確信が持てないので、実際に経路 MTU を測ります。macOS なら `ping` の `-D`（Don't Fragment／分割禁止）フラグを使うと、「このサイズのパケットはそのまま通るか？」を確認できます。

📘 **ざっくり解説：Don't Fragment（DF）とは**
通常、大きすぎるパケットは経路の途中で自動的に分割（フラグメント）されます。`-D` を付けると「分割するな。無理なら通すな」という指示になります。これを使うと「どのサイズまでなら分割せずに通るか」、つまり経路 MTU の実測ができます。

macOS での測り方は次の通りです（`<宛先>` は到達確認できる任意のホストに読み替えてください）。

```bash
# payload 1372 バイト → IPパケット総サイズ 1400 バイト
ping -D -c1 -s 1372 203.0.113.10

# payload 1420 バイト → IPパケット総サイズ 1448 バイト
ping -D -c1 -s 1420 203.0.113.10
```

ポイントは **`-s` で指定するのは payload サイズ** で、ここに **IPヘッダ(20) + ICMPヘッダ(8) = 28 バイト** を足したものが「IPパケットの総サイズ」になる、という点です。経路 MTU と比較したいのは後者（総サイズ）なので、計算を間違えないようにします。

実測した結果はこうでした（数値は今回の環境での例です）。

| payload (`-s`) | IPパケット総サイズ | 結果 |
|---|---|---|
| 1372 | 1400 | 通る ✅ |
| 1420 | 1448 | 落ちる ❌ |

総サイズ 1400 は通るが 1448 で落ちる。つまり **経路 MTU はおよそ 1400** だと分かります。

VPN のトンネルインターフェース（macOS では `utun` という名前で見えます）の MTU も確認しておきます。

```bash
ifconfig | grep -A3 utun
# 例: utun4 ... mtu 1380
```

物理インターフェースは 1500、VPN トンネル（`utun`）は 1380。pingの実測でも 1400 付近が限界。**経路の途中に 1500 より小さい区間がある**ことが、これではっきりしました。

## 根本原因：壊れた PMTU 探索によるブラックホール

ここからが本題です。MTU が小さいだけなら、本来 TCP は自動で適応できるはずです。その仕組みが **Path MTU Discovery（PMTUD／経路MTU探索）** です。

📘 **ざっくり解説：PMTU探索と MSS**
TCP は接続のはじめに「自分が受け取れる最大セグメントサイズ（MSS）」を相手に伝え合います。MSS はだいたい「MTU − 40 バイト」です（IPヘッダ20 + TCPヘッダ20）。

問題は、両端が **1500 を前提に MSS を決めてしまう** こと。経路の途中に 1380 の区間があると、その区間で「このパケットは大きすぎる」と判定されます。本来はそこのルータが「パケットが大きすぎるから、MTU を 1380 に下げてね」という **ICMP のエラー通知**（"Fragmentation Needed"）を送り返し、送信側がパケットを小さくし直します。これが PMTU 探索です。

ところが——この **ICMP 通知が経路のどこかでフィルタされていると、送信側は「縮めてね」という連絡を受け取れません**。結果、大きなパケットは届かないのに、送信側はそれに気づかず同じサイズで再送を繰り返します。これが俗に **「PMTUブラックホール」** と呼ばれる状態です。

- 小さいパケット（短い応答）は MTU 以下なので普通に通る
- 大きいパケット（長い応答のストリーム）は無言でドロップされる
- TCP は再送するが、やはり通らない → ストール → 最終的にタイムアウトで接続が切れる

まさに今回の「短い応答はOK、長い応答だけ途中で切れる」症状と一致します。SSE で長い応答を返すときは、MSS いっぱいの大きなパケットが連続して流れます。だからこそ、短い応答（小さいパケット）は素通りするのに、長い応答だけがこのブラックホールに突っ込んで途中で切れる、という形で問題が顕在化するわけです。

加えて、VPN によっては「脅威対策（Threat Protection）」のようなトラフィック検査（DPI）機能が、ストリーミング通信に影響することがある **かもしれません**。ただしこれは確証のある原因ではなく、あくまで切り分け対象の一つとして頭の片隅に置いておく程度のものです。

## 対処：効果が大きかった順に

実際に試して効果があった順に挙げます。

### ① VPN プロトコルを NordLynx → OpenVPN(TCP) に変更（最も効果的）

今回いちばん効いたのはこれでした。NordLynx（WireGuard系・UDP）から **OpenVPN(TCP)** に切り替えたところ、症状が解消しました。

切り替え後にもう一度 ping を測ると、総サイズ 1500 バイトのパケットも通るようになっていました。

理由はこう理解しています。OpenVPN(TCP) は **VPN のトランスポート自体が TCP** なので、パケットの分割・再送・順序制御を TCP レイヤーが面倒を見てくれます。アプリから見た大きなデータも、トンネルの中で TCP がうまく刻んで運んでくれるため、**DFブラックホールのような「無言ドロップ」が起きにくくなります**。

📘 **補足：それなら常に OpenVPN(TCP) が良いの？**
一概にそうとは言えません。「TCP over TCP」は二重に再送制御がかかるため、回線が不安定なときに性能が落ちる（TCP meltdown）こともあり、一般には UDP ベースのほうが高速とされます。**普段は NordLynx、AI ツールで切断が起きるときだけ OpenVPN(TCP) に切り替える**、という運用も選択肢として現実的かもしれません。ご自身の環境で実測しながら判断するのが確実です。

### ② VPN の「脅威対策（Threat Protection）」を切り分けてみる

トラフィック検査系の機能がストリーミングに影響していないか、原因の切り分けとして一時的に OFF にして挙動を比べてみるのも一手です。これは確実な対処というより、可能性を一つずつ潰すための確認という位置づけで、常時 OFF を推奨するものではありません。

### ③（一般論）インターフェースMTU/MSSクランプの調整

ルータやファイアウォールを自分で管理できる環境なら、**MSSクランプ（MSS clamping）** で TCP の MSS をトンネル MTU に合わせて強制的に小さくする、という王道の対処もあります。「経路の最小 MTU に合わせて、最初から小さいセグメントで送る」設定です。クライアント単体の VPN アプリでは触れないことが多いので、今回は ① が現実解でした。

## コラム：固定IP/専用IPは「出口IP」が変わることがある

ここで一つ、ハマった話を共有します。

NordVPN には **専用IP（Dedicated IP）** のオプションがあり、「常に同じ出口IPで通信したい」用途（許可IPリストへの登録など）で使っている方も多いと思います。私もそうでした。

ところが、**プロトコルを OpenVPN(TCP) に切り替えて再接続したら、通常サーバにつながってしまい、出口IPが別物になっていました**。専用IP は特定のサーバに紐づいているため、プロトコルや接続先サーバの選び方を変えると、意図せず通常サーバ経由になり出口IPが変わってしまうことがあるのです。

許可IP設定など「固定IP前提の運用」をしている場合、これは見落としやすい落とし穴です。私の場合は、再接続時に **専用IPのサーバを明示的に選択** することで元の出口IPに戻せました。プロトコルを変えたあとは、出口IP（`curl ifconfig.me` などで確認できます）が想定通りか一度チェックしておくと安心かもしれません。

```bash
# 現在の出口IPを確認
curl -s ifconfig.me
```

## まとめ：AIツールがVPNで固まったら、まずMTUを疑う

今回の学びを一般化すると、こうなります。

- 症状が **「短い通信はOK、大きい通信だけ途中で切れる」** なら、MTU/フラグメントを疑う
- `ping -D -c1 -s <payload> <宛先>`（payload + 28 = 総パケット長）で **経路MTUを実測** できる
- WireGuard系VPN はトンネルMTUが 1500 未満になりがちで、**PMTU探索が壊れているとブラックホールが起きる**
- 手早い回避策は **VPNプロトコルを TCP ベース（OpenVPN(TCP)）に切り替える** こと
- **脅威対策（DPI）** がストリーミングに影響していないかも、念のため切り分ける
- **専用IP運用では、プロトコル変更で出口IPが変わる**ことに注意

そして大事なのは、これは **Claude Code 固有の問題ではない** という点です。SSE やロングポーリングで応答をストリーミングする AI ツールやアプリ全般（各種 AI CLI、ストリーミングAPIを叩くクライアント）に共通して当てはまります。

もし「VPN を使うと AI ツールが固まる・途中で切れる」という現象に遭遇したら、Anthropic 側や AI ツール側の不具合と決めつける前に、**まずは MTU を疑って ping で実測してみる**——それが遠回りに見えて一番の近道だったりします。同じ症状で困っている方の助けになれば幸いです。
